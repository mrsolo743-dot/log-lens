# Как устроен log-lens

## Общая схема

```text
файлы / stdin ──► parser.read_entries ──► EntryFilter ──┬──► Analyzer  ──► Stats ───┐
  (.log, .gz)       (LogEntry)            (фильтры)     └──► Detector  ──► Finding ─┤
                                                                                   ▼
                                                     Report ──► to_text / to_json / to_html
```

Данные идут **потоком**: записи читаются генератором и сразу попадают в анализатор и детекторы. Все записи в памяти не хранятся (исключение — `--last`, о нём ниже), поэтому утилита справляется и с логами на сотни мегабайт.

## Модули

### `parser.py`: разбор строк

- Каждый формат описан регулярным выражением с именованными группами (`ip`, `time`, `request`, `status` …). Строки в кавычках разбираются шаблоном `(?:[^"\\]|\\.)*`: он корректно обрабатывает экранированные кавычки `\"`, которые nginx вставляет в User-Agent.
- **Автоопределение формата.** Регулярные выражения пробуются по порядку `timed → combined → common`. Если подошло не первое, оно переносится в начало списка, поэтому на однородном логе дальше проверяется только одно выражение.
- **Пользовательский формат** (`compile_nginx_format`). Строка `log_format` nginx превращается в регулярное выражение: известные переменные (`$remote_addr`, `$status`, `$request_time` …) получают свои группы, неизвестные попадают в `LogEntry.extra`. Если не хватает обязательных полей, выводится понятная ошибка.
- **Битые строки** не роняют программу: они считаются в `parser.malformed`, а первые пять сохраняются как примеры для диагностики.
- `open_log` распознаёт gzip по «магическим» байтам `1f 8b`, а не по расширению, поэтому подходят и ротированные `access.log.2`.

### `filters.py`: фильтры

`EntryFilter` при создании один раз компилирует условия в список функций-проверок, а на каждой записи только вызывает их. Статусы задаются гибким синтаксисом (`4xx,301`, `500-599`, `!2xx`), IP — подсетями через модуль `ipaddress`, поэтому работает и IPv6. Даты без часового пояса трактуются **в поясе самого лога**: CLI берёт первую запись и использует её `tzinfo`. Так `--since 2026-11-01` означает полночь по времени сервера, а не UTC.

`--last 24h` отсчитывается от **последней записи** лога, а не от текущего момента. Так можно анализировать и архивные логи. Ради этого записи при `--last` загружаются в память: нужно знать максимум времени до фильтрации.

### `analyzer.py`: статистика

Все счётчики построены на `collections.Counter`, и каждая запись проходит за O(1). Временная шкала сначала копится **по минутам**, а в `result()` укрупняется до шага, при котором на графике получается не больше ~200 точек (`choose_step`: 1 мин, 5 мин, 15 мин, 1 ч … 7 дней). Округление идёт по *локальному* времени записи, поэтому суточные интервалы начинаются в полночь, а недельные — в понедельник. Для перцентилей времени ответа хранится не больше 100 000 значений, чтобы ограничить память.

### `detectors.py`: подозрительная активность

| Детектор | Логика |
|---|---|
| `scanner` | регулярное выражение по известным «приманкам» (`/.env`, `/.git/`, `wp-login.php`, `../` …); от одного IP нужно не меньше 5 обращений. Если сервер ответил на такой путь кодом < 400, уровень сразу «высокий»: файл мог реально утечь |
| `bruteforce` | POST на пути с `login/auth/signin/...`; **скользящее окно** 10 минут (`_max_window` на `deque`). Успешный ответ в серии — признак подобранного пароля |
| `404-burst` | то же скользящее окно (5 минут) для ответов 404. IP, уже помеченные как сканеры, пропускаются, чтобы одно событие не дублировалось |
| `rate` | счётчик по паре (IP, минута) |
| `spike` | среднее и σ по **всем минутам диапазона, включая пустые** (иначе среднее завышается); минуты выше `mean + 4σ` склеиваются в эпизоды |

Уровень (`low/medium/high`) зависит от того, во сколько раз превышен порог: в 2 раза и больше — «средний», в 5 и больше — «высокий». Пороги настраиваются флагами CLI.

### `report.py`, `html_report.py`, `svg.py`: вывод

- `Report` объединяет статистику, находки и метаданные (файлы, фильтры, битые строки). Все три формата строятся из одного объекта.
- Текстовый отчёт рисует полосы символами `█▏▎▍▌▋▊▉` с точностью до 1/8 символа. Цвет включается, только если вывод идёт в терминал и не задана переменная `NO_COLOR`.
- HTML — **один автономный файл**: CSS, JS и SVG встроены, внешних запросов нет. Отчёт можно отправить по почте или открыть офлайн.
- Графики (`svg.py`) строятся на Python в виде SVG. Цвета в SVG не зашиты: элементы получают CSS-классы, а палитра задаётся CSS-переменными, поэтому тёмная тема переключается без перерисовки. Подсказки сделаны встроенными `<title>`, без JS.
- JS в отчёте небольшой: сортировка таблиц, фильтр строк и переключатель темы (запоминается в `localStorage` и обёрнут в `try/catch`).
- Всё, что пришло из лога (пути, User-Agent), экранируется через `html.escape`. Злоумышленник может прислать `GET /<script>...`, и без экранирования отчёт превратился бы в XSS. Это проверяет отдельный тест.

### `generator.py`: тестовые логи

Генератор детерминирован (`seed`) и отбирает время по суточному профилю (метод отбраковки с гауссовым пиком около 15:00). Браузеры подгружают статику, есть боты и ошибки 4xx/5xx, а также четыре сценария атак: сканер, подбор пароля, перебор файлов и флуд. Все IP взяты из диапазонов RFC 5737 для документации, поэтому в примерах нет адресов реальных людей.

### `cli.py`

`argparse` с подкомандами `analyze` (`a`) и `generate` (`gen`). Формат вывода определяется по расширению `-o`. Коды выхода: `0` — успех, `2` — ошибка параметров или файла, `3` — сработал `--fail-on`, `130` — Ctrl+C.

## Ключевые решения

1. **Без зависимостей.** Утилиту можно скопировать на любой сервер с Python и сразу запустить, не возясь с `pip install` от root.
2. **Потоковая обработка** вместо pandas: память не зависит от размера лога.
3. **SVG на сервере, а не JS-библиотека графиков.** Отчёт лёгкий (~70 КБ), открывается без интернета, и графики можно проверить обычными тестами.
4. **Один объект `Report` для трёх форматов**, поэтому JSON и HTML всегда показывают одни и те же цифры.

## Тесты

- `test_parser.py`: форматы, экранирование, битые строки, gzip, пользовательский `log_format`.
- `test_filters.py`: синтаксис статусов, даты и пояса, IP и подсети (включая IPv6), комбинации фильтров.
- `test_analyzer.py`: перцентили, шаг и округление шкалы, итоговая статистика.
- `test_detectors.py`: каждый детектор отдельно, отсутствие ложных срабатываний на чистом трафике, дедупликация и сортировка.
- `test_report.py`: текст, JSON, HTML (самодостаточность, экранирование XSS), SVG, сквозной тест на сгенерированном логе.
- `test_cli.py`: все режимы CLI, gzip, stdin, фильтры, `--fail-on` и ошибки.
- `test_html_browser.py`: Playwright открывает отчёт и проверяет сортировку, фильтр, тему, консоль и мобильную ширину.

## Что можно улучшить дальше

- **Режим `--follow`** (как `tail -f`) с обновлением сводки в терминале в реальном времени.
- **GeoIP:** страна по IP через локальную базу MaxMind GeoLite2 (опциональная зависимость) и карта в отчёте.
- **Сравнение двух периодов** («эта неделя против прошлой») с процентами изменений.
- **Белый список** IP и User-Agent для детекторов (свои мониторинги, CI).
- **Конфиг-файл** (`log-lens.toml`) с порогами и форматом, чтобы не передавать флаги каждый раз.
- **Многопроцессорный разбор** больших файлов по чанкам через `multiprocessing`.
- **Уведомления:** отправка находок в Telegram или на почту при запуске из cron.
- **GitHub Actions:** запуск `ruff` и `pytest` на Python 3.9–3.13 при каждом push.
